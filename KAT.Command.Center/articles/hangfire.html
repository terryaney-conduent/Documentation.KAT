Hangfire

The background jobs each Hangfire node has run in the last day: what succeeded, what failed and why, what is running now and which recurring schedules it holds - and, where Sentinel allows you, the controls to trigger, delete, create and edit them.

What it shows

Every job and schedule comes from Sentinel. Command Center signs in to each node's Sentinel endpoint with your KAT Management credentials (Settings > Profile). It never talks to Hangfire directly.

The nodes are the ones you add under Settings > Sentinel · Hangfire. They do not depend on the selected site, and switching sites changes nothing here. Each node's summary is read every Refresh every seconds, whichever page is showing.

The KPI tile

The Dashboard tile, titled Hangfire · {Name}, shows one node at a time. With more than one configured, the dots and arrows along its footer switch between them, and each dot takes the colour of its node's state. Clicking the tile opens this page on that node. With no nodes configured the tile is hidden, and this page points you to Settings.

  • 24h Completion - jobs that succeeded across the chart's 24 hours. The oldest hour may be partial.
  • {N}d Failures - failed jobs within Failures within days (Settings), red when there are any. 100+ means at least that many; the page lists them all.
  • Processing - jobs running now. Recurring - the node's recurring schedules.
  • The chart plots succeeded and failed jobs over the last 24 hours.
  • When a read fails, the tile shows why and when the node last answered.

Reading the page

Show node picks the node. The header chips Succeeded and Failed count that node's jobs; click one to show only those jobs, and click it again to show every job. Processing counts the jobs running now and is not a filter. Filter by ID or name narrows either list as you type.

The chart plots succeeded and failed jobs over the last 24 hours. Click Succeeded or Failed below it to hide or show that line.

Jobs and Recurring

Two tabs below the chart hold the lists. Click a column heading to sort. In a narrow window each row becomes a card and Sort joins the header.

  • Jobs - the node's succeeded and failed jobs, newest first: Job ID, Name, Finished, State and Duration.
  • Recurring - the recurring schedules: ID, Cron (hover for a description), Created, Next Run, Last Run and Last State. Last State shows Succeeded or Failed while Hangfire still holds the last job it started, and is blank once that job has expired or before the schedule first runs.

The lists load when you open the page, change node, tab or filter, refresh, or finish an action. Between those, the chips, chart and tile keep refreshing but the rows do not.

Move between rows with j / k. Enter opens a row's details, and Space opens its menu (or ticks it while choosing a batch).

Details

Click a row, press Enter on it, or choose Open from its menu.

  • A job shows its node, when it was created, its duration and the recurring schedule that started it. History lays out every state it passed through with the time spent in each, then the exception and stack trace of a failed run and the console output of each run, as Hangfire's dashboard shows it (with Copy). The newest run comes first; select Show outdated console to see an earlier run's output. Configuration lists its parameters and invocation XML.
  • A recurring job shows its cron, next and last run, when it was created and updated, and any schedule error. Last Run names the job it last started and how long that job ran, then its history, and Configuration its parameters. When the schedule has not run, or that job has expired, only Configuration is shown.

The actions you can take on the item sit in the footer.

Limits

  • The Jobs list holds the newest 2,000 jobs. When a node has more, the footer reads Newest 2,000 of N; filter to find older ones.
  • A failed job's Duration stays blank in the list until Sentinel reports it. Its details still show how long its last run took.

Actions

You only see the actions Sentinel's Hangfire permissions give you on that node, and some apply only to certain jobs. Sentinel checks again when the action runs. A row's menu opens from the … button at the start of its row.

  • Trigger Now - runs a recurring job once now, outside its schedule. It is offered on the Recurring tab only.
  • Edit - changes a recurring job (see Creating and editing).
  • Delete Job - removes a succeeded or failed job. This cannot be undone.
  • Delete Schedule - removes a recurring schedule. Jobs it already queued are not deleted.

Delete always asks you to confirm. Triggering a single schedule asks too, unless you choose Don't ask me to confirm triggers; turn it back on with Confirm Trigger in Settings. A batch trigger always asks.

Batch actions

On the Jobs tab, Delete Jobs starts selecting jobs to delete. On the Recurring tab, Batch Action offers Trigger Now and Delete Schedules; its main button repeats the last one you chose.

  1. Choose the action. Only rows it applies to get a checkbox, and row menus are hidden; tick them, or tick All.
  2. Continue lists what will change. Untick anything you want to leave, then confirm.
  3. While it runs, the strip counts progress and failures. Cancel after current batch stops before the next group of jobs; anything already sent still applies.

A schedule that was triggered shows a green Triggered beside its ID for a few seconds. Each job or schedule that did not succeed gets its own result on its row, with the reason: skipped (amber) when Sentinel passed over it or your access no longer allows it, failed (red) otherwise. Rows that were deleted, or were already gone, leave the list; triggering a schedule that was already deleted elsewhere also shows a warning above the list. A summary above the list counts what completed, failed, was skipped and never started.

Nothing changes on the page until Sentinel answers; the list then reloads.

Creating and editing

Create appears on the Recurring tab when you may create jobs on the node. Both Create and Edit start by asking for the job assembly: an Administration.{Client}.dll in a site's bin folder. The browser opens in the Admin source folder (Settings), or the client's bin folder when editing. Command Center reads the assembly's job types without running it, and the client's Configuration.xml decides whether a job type is a Report. An assembly that cannot be used says why, and the form does not open: above the list for Create, on the job's row for Edit.

Job Type, Suffix
Create only. The recurring ID is {Client}.{Job Type}, plus .{Suffix} when one is given (letters, digits, _ or -) so one job type can run on several schedules.
Cron
When it runs, in Central Standard Time. CRON Syntax Help opens a cron reference.
Run as a QA Job
Tells the job it is running for the QA (test) site. Off by default.
Process FTP
Report jobs only.
Inputs
Name and value pairs passed to the job; a value can be text, True or False. Start a name with @ to promote it to a root-level element. Names must be unique, valid XML names, and not one the job type already generates.

Edit reads the job's current settings from Sentinel, so the form starts from what is actually scheduled. A job that was not created from a job package (for example one registered in code) can't be edited here.

Create will not use the ID of a job that already exists: the form says so under Suffix, so edit that job or choose a different suffix. Sentinel checks again when saving, so a job created elsewhere during the upload is not replaced and the rejection also appears under Suffix. Save on a job that was deleted elsewhere while you edited it creates it again. Once saved, the form closes and the list reloads with the job. If Sentinel rejects the job, the form stays open with the reason and nothing changes; if it does not answer, the change may still have applied, so check the list before trying again. The assembly you chose stays inside Command Center until it is sent, and is never saved or logged.

When it refreshes

Every node is read every Refresh every seconds, whether or not the Dashboard or this page is showing. ↻ and F5 read now and reload the list. A failed read never raises a warning; the page and tile show it instead, and What's Happening lists a node that is unreachable, denied, not configured or failing to read Hangfire, or that has failed jobs within Failures within days.
