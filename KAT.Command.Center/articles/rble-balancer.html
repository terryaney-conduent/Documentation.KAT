RBLe Balancer

How each RBLe Balancer is spreading requests across its nodes right now: which nodes are healthy, how busy each one is, how fast it answers, and - if you are a balancer King - the controls to take nodes out of rotation, bring them back and replace their settings files.

What it shows

Every number comes from Sentinel. Command Center signs in to each balancer's Sentinel endpoint with your KAT Management credentials (Settings > Profile) and reads the balancer's status every few seconds. It never talks to a balancer or an RBLe node directly.

A balancer runs on every web server behind your load balancer. Command Center reads one web server's balancer at a time: the one chosen in the Host picker, which starts on the first host listed in Settings. Sentinel reads that web server's balancer directly, whichever web server handled the request.

The balancers are the ones you add under Settings > Sentinel · Balancer. They do not depend on the selected site, and switching sites changes nothing here. Status is read only while the Dashboard or this page is open.

The KPI tile

The Dashboard tile, titled RBLe Balancer · {Name}, shows one balancer at a time. With more than one configured, the dots and arrows along its footer switch between them; the tile never advances on its own. Clicking it opens this page on that balancer. With no balancers configured the tile is hidden, and this page points you to Settings.

  • The compact chip beside the balancer name shows the selected host's service health, using the same labels and colors as the page. The header counts nodes by state, including Heavy and Stressed. Every node out of rotation counts as Offline, whatever the reason.
  • The total uses the chosen period. With room beside the request counts, each node gets a colored beam scaled to the busiest node. In tighter tiles a full-width distribution bar above the rows instead shows each node's percentage of all requests. Hover either for its figures.
  • Each row shows its state dot, colored balancer icon and node name, CPU and memory meters lined up just after the longest name, its gate (see Capacity), a separate Rate column, Requests and 60s Avg. Node names shorten when space is tight; their full names remain on hover. Hover the meters for load readings and the Requests area for counts and response time. A red meter appears only when the chosen period has failures; its fill still represents failures among the last 50 completed requests. Response time turns amber at 650ms and red at 800ms, with colored values in bold.
  • Below the node rows, a Totals row covers every node on the shown host, even when the tile lists only the first eight; with more than one host a Farm Estimate row follows. Each reads like a node row: the request rate, average CPU and memory meters, requests in flight under the gates, then the requests. The Farm Estimate shows no CPU, memory or average response time. Hover a totals row for its figures and how the estimate is made (see Totals).
  • The picker beside the refresh button chooses the period the requests are counted over; it is shared with the page (see Request counts).
  • When a read fails, the tile says so and keeps the last reading it has, dimmed.

Reading the page

The header chips count nodes by state: Healthy, Heavy, Stressed, Unhealthy, Offline and Unknown. Click one to show only those nodes; click it again to show every node.

The Balancer picker's edge dot reports the most severe issue across all configured balancers, even when the selected balancer is healthy: red takes priority over amber. Dots inside the dropdown describe each individual balancer.

Below them, Balancer picks which balancer to show and Host which web server Command Center reads. Choosing another host starts its charts over from its next reading, and the Dashboard tile follows the same host. The choice lasts until the app restarts. The identity line names the balancer and its version, truncating long text with the full value on hover; the cluster name sits below, left-aligned. On the right, a chip shows that host's balancer service health, with Polled at {time} below it. This is when Command Center received the displayed snapshot; failed polls and cached duplicate replies do not advance it.

The host chip reads Online (Sentinel's Active state), Draining (offline with requests still in flight), or Drained (offline with no requests in flight). This is the whole balancer service's health, separate from each node's state. Older responses without health show Unknown, and an unrecognized value is shown as received; the current-host toggle is disabled until health is known.

Banners

  • Unknown host (amber) - a web server that is not in the balancer's Hosts answered for the chosen host, usually because a name in Settings is not that web server's machine name. The page keeps working and shows that web server's numbers; it also joins the Host picker and every action's server list. Add it to the balancer in Settings, or dismiss the banner; dismissing also removes its What's Happening row until the app restarts.
  • Balancer settings not applied - the balancer rejected its own configuration and lists why.
  • Stale - the last read failed, so the page is showing older data. All changing table/card readings, meters and charts dim until a successful poll; names and controls remain usable.
  • Gate-aware routing is off - the cluster does not use the LoadAware policy, so nodes cannot be taken offline from here.

Charts

Response Time, CPU Load and Request Rate all follow the Requests picker: one-minute points for Last 15 minutes, and half-hour points for Last 12 hours and Since start. For Last hour, CPU keeps all 60 one-minute points so a peak identifies its minute; response time and request rate use four-minute points. Plotted history never extends beyond twelve hours; the oldest overlapping half hour is omitted when its aggregate could include older readings. History comes from the balancer, not from how long Command Center has been open.

The charts stay in one row. Three fit in a wide window, then two or one as space narrows. When some are offscreen, the previous/next arrows move the first chart one position, or choose a clock, CPU Load or request-count icon to bring that chart first. They never advance automatically. Each node keeps its colour; clicking its colored balancer icon includes or excludes that node from chart comparisons. Hover details anchor below the time labels instead of covering the plotted lines.

Response Time divides each bucket's total response milliseconds by its completed requests, including failures and gate queueing. Four-minute points weight the underlying minutes by their request counts. Empty buckets are gaps. The title remains the current weighted 60s Avg for reporting nodes in rotation, regardless of the picker; it becomes a dash when there are no recent completions.

CPU Load averages fresh load samples for each node, weighted by sample count when minutes are combined. Its vertical axis extends 5 percentage points below the lowest visible plotted value and 5 above the highest, capped at 0–100%; a 13.6% maximum gives an 18.6% upper limit. An idle node can still report CPU. No samples means a gap, while a sampled 0% is a real point. Reset Counts preserves CPU history; a balancer restart or removing and re-adding a destination starts it over. No additional load-endpoint probes are needed.

Show Peaks, at the right of the CPU Load title, adds a smooth translucent area from each node's average up to its highest observed CPU reading in that bucket. Areas overlap rather than stack, and the axis includes visible peaks while the switch is on. Every node's hover details include its peak even with the switch off. Short windows identify the minute; twelve-hour and Since start views identify the half hour. A peak does not show when within that bucket CPU spiked or how long it stayed high; smooth curves are visual interpolation, not extra samples. Missing or invalid peak data stays unavailable rather than being inferred from the average. Both Balancer and Sentinel need the updated status contract to supply peaks.

Request Rate plots successful requests per hour in every window, so changing the bucket width does not change the units. Each point divides its successful count by the time actually covered, accounting for the selected window, collection start and available history. The developing point uses elapsed time at the balancer's snapshot and is marked projected; zero elapsed time remains a gap until a rate can be calculated. Every tooltip retains actual successes and failures. The separately labeled total remains an actual request count, including failures, for the selected period across every host node; Since start keeps the lifetime total even though the chart stops at twelve hours. Request beams also remain actual counts.

Show Total, at the right of the Request Rate title, adds a neutral line summing successful requests per hour across every node on the shown host. It includes hidden and offline nodes and remains available in extremes mode. It is a rate, not the actual-count headline; a point stays a gap if any node lacks rate data.

Show Extremes, at the right of the Charts bar above the charts, shows each chart's lowest and highest node averages over the selected plotted window, not whichever nodes happen to be lowest and highest at each point. Excluded nodes and nodes without observations do not participate. With more than three eligible nodes, a dashed line adds their average: CPU weights samples, response time weights completed requests, and Request Rate averages the individual node rates. Tooltips state how many eligible nodes contributed to a point. CPU peak areas follow the selected nodes without changing their average-based ranking; the dashed node-average line has no invented peak. All three switches start off, remain selected through polls and window changes, and are not saved to Settings.

The developing point and isolated observations remain visible. CPU and response points show their observed averages while filling. Empty activity is distinguished from unavailable or malformed history, and partial-node coverage is named; an unavailable caption does not by itself prove a component needs upgrading. Buckets before collection started are gaps.

Request counts

The Requests picker (under the page's header, and on the Dashboard tile beside its refresh button) chooses the period every Requests count covers: Last 15 minutes, Last hour, Last 12 hours or Since start, counted since the balancer started or its counts were last reset. The node rows, the totals, the Farm Estimate and the selected node's details all follow it, and the tile and the page always show the same period. It lasts until the app restarts and does not change the saved setting. The default is Last hour, configurable under Settings > Sentinel · Balancer > Request Counts; saving a different default replaces the current choice.

The windows are counted by the balancer in whole minutes, so a window holds between N-1 and N minutes of traffic. Windows count a request when it completes, while Since start counts it when it begins, so a request still running appears only in Since start. Red failure meters and the recent-failure tooltip always use the last 50 requests, whatever the period. A balancer or Sentinel that has not been updated to report windows shows a dash instead of a count for the shorter periods; Since start still works.

The total and distribution bar use the same period across every node on the shown host, including historical traffic on offline nodes. The detail panel's Share is the node's percentage of that total. In table view, per-node beams replace the distribution bar when each beam can be at least 70px wide; the KPI tile uses 100px of spare width. Cards always show beams. These beams compare each node with the largest node count, not with the total. Only the solid colored length is drawn, without an unfilled remainder. Filters, hidden chart lines and the KPI's eight-row limit never change either scale. Zero traffic has no percentage and draws no bar. If any node lacks the chosen count, the scale is unavailable rather than being recalculated around the other nodes.

The selected node's byte totals follow the same period: ↑ means sent and ↓ means received, with those labels available on hover and to screen readers. Bytes are counted when each forwarding attempt finishes, including failures and retries; Since start uses cumulative bytes. They measure bodies sent to and received from the node, not headers. An older Balancer or Sentinel may report window request counts without byte totals; missing byte values show a dash rather than lifetime totals.

Req/s follows the same picker: the selected request count divided by the seconds covered by the reading, starting no earlier than Reset Counts or restart. Shorter periods include the current partial clock minute; Since start uses elapsed time since the counts started. The KPI headline, rows, Rate sorting, totals and Farm Estimate use this average, including historical traffic on nodes that are now offline. Missing counts or no elapsed time show a dash, not a live-rate fallback. A stale reading keeps its rate until a new reading arrives. Only 60s Avg retains its separate period.

Nodes

Table meters share a track after the longest node name, just like the Dashboard tile. Cards keep capacity immediately after the name and always show aligned request beams after capacity, including when details expand below the node. Colored 60s Avg values are bold in the table, cards, expanded details, sidebar and KPI; neutral readings keep their normal weight.

The table columns are Node, Capacity, In Flight, Rate, Requests, 60s Avg and State. 60s Avg divides the total response time by completed requests in the last 60 seconds, including failures and time queued at the gate. Hover its label on either surface for the calculation and how totals weight each node by its completed request count; hover a table value for the number of requests behind it. The Requests period does not change this average. A node with no completed requests in that minute shows a dash. Table values above 9,999ms show 9,999!ms; hover for the exact value. CPU and memory mini-meters align after the node name; hover them for their readings. Click a node, or move to it with j / k, to see its details beside the list. Where the table cannot fit, rows become cards without dropping readings. In a narrow window the details open below the node instead: click its expand control or press Enter.

CPU and memory both turn amber from 70% through 90%, and red above 90%. Either amber reading makes an in-rotation node Heavy; either red reading makes it Stressed. Unhealthy and offline states take precedence. The state chip and detail-panel dot share this result, with a tooltip identifying each elevated resource. CPU and memory values in cards and details are also bold and colored when elevated.

When a node has any failed requests in the chosen request period, a small red meter appears beside its request count; with no failures in that period there is no meter. Each failure in the node's last 50 completed requests fills another 2% of the meter, so it can be empty when the failures are older than those 50. Hover anywhere in the Requests cell, including the count, for recent and period failures. Before 50 requests have completed, the tooltip names the smaller sample. If Balancer/Sentinel does not report recent outcomes, or no request has completed to sample, the meter has a dashed red outline and an unavailable message rather than an empty reading. Both RBLe Balancer and Sentinel must be deployed with the updated shared status contract to supply these counts.

The sidebar's node header shows a glowing state dot on the right; hover it for the state and its explanation. The detail card keeps the cumulative N failed count in normal text. Only when recent failures exist does it add M in last 50 in red, after a normal-colour separator. Reset Counts clears the cumulative count, the recent window, the request windows and traffic charts, and restarts the average response minute. CPU history is preserved.

Health Checks lists Health Endpoint (active endpoint checks), Load Endpoint (retrieving the node's load readings) and Request Forwarding (transport errors while forwarding requests, not HTTP error responses). Load Endpoint shows Healthy when the latest read succeeded, Not received yet before a reading arrives, or a consecutive failure count with the error in its tooltip. Its Healthy label describes reporting, not low CPU or memory usage. Polling Age shows when the Load Endpoint was last read and when the node's Gate Counts last arrived, either from that read or from a forwarded response.

Healthy
In rotation and passing its health checks.
Heavy
CPU or memory is 70-90%, with neither above 90%.
Stressed
CPU or memory is above 90%.
Unhealthy
In rotation but failing an active or passive health check.
Unknown
In rotation, with no health result yet.
Draining
Taken offline. Requests already running finish; no new requests are sent.
Drained
Taken offline and no requests are running. Safe for maintenance.
App Offline
The node is serving its app_offline page, so the balancer sends it nothing. Bring online cannot change this; it returns when the app does.

Totals

Totals sit at the bottom of the list and cover the nodes it shows, so a state chip narrows them too. In Flight, Rate and Requests are sums (Requests for the chosen period; a dash when any node does not report it); 60s Avg weights reporting nodes in rotation by their completed requests, so a busy node counts for more than an idle one. CPU and memory average only nodes in rotation that report a reading. Their mini-meters align with each node's meters after the name. Memory appears after CPU in the totals cards and beside CPU on the Dashboard tile. When the balancer has more than one host, a Farm Estimate row multiplies the sums by the number of hosts, assuming every host carries the same load as the one shown. Under that assumption its averages would only repeat the shown host's, so it shows no CPU, memory or 60s Avg. The totals' red meter counts failures across every node's last 50 requests, so its scale is 50 per node (times the hosts for the estimate); the tooltip states the scale. In card view the totals are two fixed cards titled with the host's name and Farm Estimate.

Capacity

Each node reports how many requests it is running and queueing against its limits (Q: queued/max, with a pip per running slot). The balancer's gate uses that reading to decide whether a node can take another request. A node with no fresh reading is skipped by retries, and one with no reading at all is rejected.

Gate retries

When a node's gate is full, the balancer can resubmit the request to another node. The section under the table says whether retries are on. Its counts, outcome percentages, extra attempts and unretried rejections follow the Requests picker, as do the Dashboard's Retried line and the selected node's rejection details. Windowed retries count a request and its extra attempts together when it finishes; Since start keeps the cumulative counters, including retries still running. If Balancer/Sentinel does not report the chosen window, it shows unavailable rather than lifetime counts.

King actions

Only a balancer King for that balancer's Sentinel endpoint sees the actions; everyone else gets a read-only page. Header actions always live in the … menu, even in a wide window, with Take Host before Take All Nodes. The menu has no scrollbar of its own; in a short window, scroll the app to reach the remaining actions. Each action names its targets and asks you to confirm. A node's menu opens from the … button at the start of its row (or press Space on the row).

  • Take Offline / Bring Online (a node's menu) and Take All Offline / Bring All Online (Take All Nodes) - stop or resume new requests to the nodes. Each comes in two forms: On the chosen host, or On All Hosts, whose confirmation warns how many nodes and hosts it changes. A node's menu offers the opposite of its state on the chosen host; its All Hosts items are always offered because other hosts may report a different state. A balancer with one host has no All Hosts form. Taking a node offline is offered only when the cluster uses gate-aware routing.
  • Reset Host Counts - start the traffic, retry and pick counts again, On the chosen host or on All Hosts. With one host, the menu has no Reset Host Counts heading and shows a single Reset host Counts action.
  • Take Host ... - Take host Offline when the shown host is Online, or Bring host Online when it is Draining or Drained. With multiple hosts, Take All Hosts Offline and Bring All Hosts Online are also available. With one host, the host action follows the reset action without a heading or separator. These change the whole service's upstream health checks on the listed hosts, affecting every cluster there without changing individual node switches. Taking a host offline drains running requests without stopping the process. Bringing it online clears the service's health-offline setting, but an offline marker file still keeps it unavailable. Both Sentinel and Balancer must support the service endpoints.

Nothing on the page changes until the next reading confirms it. If some servers fail, the dialog stays open and lists each one with what its failure means: a timeout may still have applied, while a denial or conflict changed nothing on that server.

Settings files

A balancer with a publishing node (Settings > Sentinel · Balancer) can read and replace its nodes' appsettings files. Without one these actions are unavailable.

  • View Settings (a node's menu) asks for a file name - appsettings.json by default - and downloads that node's file to your Downloads folder as {node}.{file name}. It then opens in Visual Studio Code when it is installed, otherwise in the app Windows uses for the file. If the file is already there you can replace it, save it somewhere else or cancel; with automatic opening off, a confirmation shows the saved path with Copy Path, Open Folder and Open File. These choices live under Settings > Sentinel · Balancer > View Settings Download. The node's file is never changed.
  • Update Settings (a node's menu) and Update All Settings (every node in the cluster) ask for a local appsettings*.json file, then confirm the deployment type, file name, size and nodes before replacing that file on each of them. The file must already exist on the nodes; it is overwritten whole.

A file you upload with Update Settings stays inside Command Center until it is sent. It is never shown, logged or saved.

When it refreshes

Each balancer is read every Poll Every seconds while the Dashboard or this page is showing; balancers on the same Sentinel endpoint share one read. ↻ and F5 read now. A failed read never raises a warning; the page and tile show it instead, and What's Happening lists a balancer that is stale, unreachable, denied, unhealthy or not applying its settings.
